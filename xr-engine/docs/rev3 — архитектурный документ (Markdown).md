# LIGHTWEIGHT XR CONTENT ENGINE (Android XR Edition)
Редакция 3 — с учётом ревью от 2026-09-13.

## Что изменилось в этой редакции

1. **Привязка к экрану (разд. 4):** ARCore Augmented Images убран как механизм для живого экрана — эталон обязан быть статичным, а видео меняется каждый кадр. v1: head-locked размещение + опциональный трекинг корпуса телефона как физического объекта. Кастомный CV-детектор «прямоугольника экрана» — отдельный R&D-трек в roadmap, не часть v1.
2. **Словарь жестов (разд. 2, 6):** зафиксирован под пользовательский цикл «свайп — смена XR-слоя, следующий свайп после последнего — скрытие». Свайп теперь навигация по слоям, а не запуск анимации.
3. **Сценарий B (разд. 5, Phase 3):** явно зафиксировано отсутствие публичного cue API у Netflix и аналогов; инженерный трек заблокирован до BD; описан контракт API, который выносится на переговоры.
4. **Сценарий A (разд. 5, 9):** добавлены требования к UX согласия MediaProjection (foreground service, явное разрешение, видимый индикатор).
5. **Дополнение от 2026-09-16 — On-device SLM intent layer (разд. 6, Phase 2.5):** roadmap-трек на замену эвристических порогов классификаторов жестов резидентной в NPU-памяти SLM класса 3B (фьюжн поз руки + аудиоконтекст + состояние таймлайна). Gated on партнёрское железо с ≥12 ГБ unified memory; Android-аналог — Hexagon NPU (целевая платформа — Android XR, не iPhone).

## ВВЕДЕНИЕ

«Иллюзия интерактива» (Pre-baked State Machine) остаётся верным подходом для лёгких Android XR устройств: очки не считают физику и коллизии в реальном времени, а просто переключают заранее просчитанные (pre-baked) состояния по триггеру. Это тот же принцип, на котором больше десяти лет держится динамическая вставка рекламы в онлайн-видео (стандарты VAST/VMAP у YouTube и других платформ): готовый креатив заранее лежит в системе, привязан к таймкоду или событию, и в нужный момент просто подставляется. Изобретать здесь ничего не нужно — паттерн уже обкатан индустрией на миллиардах показов.

Пользовательский цикл, зафиксированный как требование v1: поверх контента заранее вставлено ~10 XR-слоёв (аналог рекламных вставок); мах ладонью (свайп) — смена XR-слоя; свайп после последнего слоя — скрытие; удержание ладони — скрыть немедленно.

Архитектура разделена на два независимых сценария синхронизации:

- **СЦЕНАРИЙ A** — контент без DRM (обычные ролики YouTube, TikTok, Instagram/Reels, любой UGC). Устройство само распознаёт, что и когда идёт, локально на смартфоне.
- **СЦЕНАРИЙ B** — DRM-контент премиальных стримингов (Netflix и аналоги). Локальное распознавание физически заблокировано платформой на уровне ОС, поэтому нужен сигнал от партнёра.

XR-часть (pre-baked стейты, тонкий рендер-клиент на очках, свитчер слоёв) у обоих сценариев одна и та же. Разница только в том, откуда приходит триггер «что и когда показывать» — это и есть главный нерв всей архитектуры.

## 1. CREATOR / CONTENT LAYER (Подготовка «Иллюзии»)

Авторы создают State Bundle (пакет состояний). Два разных по стоимости класса ассетов:

- **Base Asset (GLB):** лёгкий skinned-mesh с baked skeletal-анимациями (Appear, Idle, React). Зрелый стандартный пайплайн: сжатие геометрии (Draco/meshopt), текстуры в KTX2/Basis Universal. Оптимизация — обычный async-воркер при загрузке автором.
- **Base Asset (3D Splat / Gaussian Splatting):** визуально сильнее, но кардинально тяжелее по рантайму. Реал-тайм рендеринг сплэтов на мобильных чипах — область активных исследований 2025–2026, а не готовая коробочная технология: свежие методы показывают сотни FPS при считанных мегабайтах на сцену на чипах уровня Snapdragon 8-й серии, но каждый ассет требует отдельной офлайн-дистилляции и квантизации на десктопном GPU конкретно под эту сцену. Отдельный, более тяжёлый этап пайплайна.

**Рекомендация:** на первом релизе — только GLB, Splat выносить в roadmap отдельной строкой после обкатки на пилотных сценах.

**Asset Sanitizer:** серверная проверка на «Mesh Bombs» (лимиты полигонов/текстур), с отдельными порогами для GLB и для Splat.

## 2. CONTENT MANIFEST (Манифест сценария)

Тот же паттерн, что у видеорекламы (таймкод-триггеры в духе VAST/VMAP):

- **Video ID:** привязка к конкретному ролику. Для Сценария A — собственный ID из закрытого реестра зарегистрированного контента (не произвольное видео из интернета). Для Сценария B — Video ID и таймкод приходят готовыми от партнёра вместе с сигналом (разд. 5).
- **Timeline Events:** Video Time 12.000 → Spawn Layer_1 (State: Appear → Idle).
- **Layer Stack:** упорядоченный список слоёв (до ~10), каждый со своим State Bundle.

**Словарь жестов v1 (зафиксирован, изменению только через версионирование манифеста):**

| Жест | Действие |
|---|---|
| Swipe_Right | Следующий XR-слой (цикл 1→2→…→N; свайп после последнего — скрыть все) |
| Swipe_Left | Предыдущий XR-слой |
| Palm_Hold (открытая ладонь, удержание ~0.8 с) | Скрыть текущий слой немедленно |
| Pinch | Зарезервирован (выбор/подтверждение в будущих версиях) |

Анимационные стейты слоя (Appear → Idle → React) сохраняются, но свайп теперь — это навигация по слоям, а не запуск анимации. Переключение слоя обязано укладываться в <100 мс от детекта жеста — иначе «иллюзия» рассыпается.

## 3. THIN-CLIENT & PREFETCH ENGINE (Умная доставка)

Архитектура Thin-Client Spatial CDN с Predictive Branching Cache и Memory Eviction. Бюджет: ~10 слоёв на контент, LRU-вытеснение. Разделение ролей:

- **Смартфон (Сценарий A)** или **партнёрский сигнал (Сценарий B)** — распознавание «что и когда», решение «что триггерить».
- **Очки / проводной компаньон-блок** — рендер уже готового решения с минимальной задержкой. Финальная компоновка 3D-объекта с учётом положения головы (head-locked rendering) считается максимально близко к дисплею, а не гоняется по Wi-Fi/Bluetooth с телефона — иначе лаг и рассинхрон с движением головы.

---

## 4. SPATIAL & SCREEN ANCHORING (переработан в ред. 3)

- **Device Tracking (6DoF):** подтверждено текущим поколением — AR-очки на Android XR (старт продаж осенью 2026) заявляют hand tracking и 6DoF-трекинг через собственные сенсоры.
- **Placement v1 — Head-Locked:** объект позиционируется в системе координат вида с фиксированным смещением («10 см над экраном» имитируется без привязки к самому экрану). Плюсы: ноль зависимости от CV, работает всегда, минимальная задержка. Минусы: объект «прибит» к взгляду, а не к физическому экрану — для pre-baked слоёв приемлемо и является дефолтом v1.
- **Placement v2 (опция) — трекинг корпуса телефона:** геометрия корпуса статична и трекается надёжно 3D-объектным трекингом; даёт настоящую привязку «над экраном».
- **Что НЕ работает:** ARCore Augmented Images по живому экрану — эталон обязан быть статичным изображением, видео меняется каждый кадр и как маркер не удержится. Кастомный детектор «прямоугольника экрана» по камере очков — отдельный R&D-модуль со своей оценкой, вынесен в roadmap, не часть v1.

Разделение «где» (позиция — этот раздел) и «что и когда» (контент — раздел 5) сохраняется: визуальный канал слишком хрупок для распознавания контента (моушен-блюр, HDR-клиппинг), а для позиционирования достаточен.

## 5. MEDIA SYNCHRONIZATION (Синхронизация с плеером)

Video Clock — источник истины. Способ получения сигнала зависит от сценария.

**Сценарий A (YouTube, TikTok, Instagram, собственный UGC):**
Смартфон распознаёт собственный экран и звук штатными Android API — MediaProjection (захват экрана) и AudioPlaybackCapture (захват аудио других приложений), с явного разрешения пользователя. Сигнал сверяется с собственным закрытым реестром зарегистрированного контента (принцип коммерческих ACR-решений для второго экрана, но источник — сам телефон, а не внешняя камера; на порядок проще открытого ACR). Приоритет — аудио-фингерпринтинг (как Shazam): быстрее и дешевле по батарее, чем хеширование кадров. Play / Pause / Buffering / Seek → Freeze / Flush XR-таймлайна.

**UX согласия (новое в ред. 3):** MediaProjection требует foreground service и системного диалога разрешения. Без согласия пользователя сценарий A не стартует — это часть онбординга: объяснение зачем, явное включение, постоянный видимый индикатор активного захвата. Проектировать как требование, а не как edge case.

**Сценарий B (Netflix и другой DRM-контент, Widevine L1):**
Самостоятельное распознавание не работает в принципе: защищённая видеоповерхность отдаёт чёрный кадр при захвате, перехват звука запрещён — это штатная защита контента, обойти её штатными средствами нельзя. Единственный путь — партнёрская интеграция: платформа сама присылает cue-сигнал, как рекламные cue-точки в вещании передаются вещателем, а не вычисляются приёмником.

**Важно (ред. 3):** публичного cue API у Netflix и аналогов не существует. Это трек переговоров и партнёрства, не инженерная задача. На переговоры выносится предлагаемый контракт:

```
POST /v1/xr-cue
Authorization: Bearer <partner_token>
{
  "video_id": "string",
  "content_timestamp_ms": 1450000,
  "action": "spawn | switch | despawn",
  "layer_id": "layer_03",
  "state": "Appear"
}
```

До подписания партнёрства инженерных задач по сценарию B нет — только BD-трек. Не заявлять «работает из коробки» для DRM-платформ.

## 6. ILLUSORY INTERACTION RUNTIME (Обработка жестов)

**Input Layer:** SDK Android XR отдаёт только сырые позы 26 суставов руки по стандарту OpenXR — готовых системных событий «Swipe / Pinch / Grab» нет. Даже пинч считается вручную (расстояние между кончиками большого и указательного). Классификаторы команда строит сама поверх потока поз; часть жестовых API платформы экспериментальна и может измениться. Это своя разработка и своё время в оценке, не бесплатный слой платформы.

**Требования под словарь v1 (ред. 3):** направленный свайп — анализ вектора скорости ладони + дебаунс от дрейфа руки; Palm_Hold — открытая ладонь статична ~0.8 с; пороги настраиваются на собранном датасете жестов команды, а не «из коробки». State Switcher и Intent Matching — как в исходной архитектуре, но оперируют слоями (разд. 2), а не анимациями.

**Roadmap — On-device SLM intent layer (дополнение от 2026-09-16, Phase 2.5):** индустрия сходится на резидентных в памяти устройства SLM (тренд подтверждён анонсом Apple A20 Pro 09.2026: Dual Neural Engine 32 ядра, +50% пропускной способности памяти, on-device модели как стратегия). Следующий шаг после эвристических классификаторов — SLM класса 3B, постоянно resident в NPU-памяти смартфона, которая фьюзит три сигнала: позы 26 суставов руки, аудиоконтекст (таймкод из фингерпринтинга) и состояние XR-таймлайна — и выдаёт intent напрямую в State Switcher. Выигрыш: отпадает ручной тюнинг порогов под каждого пользователя, ложные срабатывания падают, инференс остаётся локальным (приватность разд. 9 сохраняется, облачного round-trip нет — бюджет <100 мс соблюсти проще). Gated on: партнёрское железо с ≥12 ГБ unified memory; на целевой Android XR-платформе аналог — Hexagon NPU (Snapdragon), не Apple Silicon. Не часть v1/v2, инженерный старт — после обкатки эвристических классификаторов на датасете команды.

## 7. LIGHTWEIGHT RENDERING & COMPOSITING

Без изменений. Video Environment Probe (динамическое освещение по цвету края кадра) и LOD Manager с Distance Culling — стандартные проверенные паттерны: первое — аналог light estimation в AR-SDK, второе есть в любом игровом движке.

---

## 8. BACKEND (Стек)

FastAPI / Redis / Celery — зрелый и достаточный выбор для манифестов, сессий и асинхронной оптимизации ассетов. В Phase 3 добавляется stub-приёмник `POST /v1/xr-cue` с проверкой партнёрского токена (сценарий B).

Терминология: совместный просмотр несколькими зрителями — **Co-Viewing Sync** (Redis pub/sub для синхронизации состояния между сессиями). Название «SharePlay» не использовать — это бренд Apple.

---

## 9. ПРИВАТНОСТЬ

Сценарий A требует доступа к экрану и звуку смартфона — проектировать как приоритет с самого начала: fingerprinting выполняется локально на устройстве, сырые кадры и аудио никуда не выгружаются, у пользователя — явное согласие и видимый индикатор активности (см. также UX согласия в разд. 5).

## COMPLETE RUNTIME FLOW

**Сценарий A (соцсеть / UGC):**
1. Зритель в очках Android XR скроллит ленту на смартфоне (согласие на захват дано при онбординге, индикатор активен).
2. Смартфон через AudioPlaybackCapture (приоритет) / MediaProjection распознаёт: зарегистрированный ролик X, секунда 8.
3. Thin-Client CDN заранее подгружает слои 1–3 (бюджет ~10, LRU).
4. На 10-й секунде движок спавнит слой 1 head-locked со смещением «над экраном», стейт Appear → Idle, динамический свет от кадра видео.
5. Свайп вправо — мгновенное переключение на слой 2 (<100 мс, pre-baked стейт).
6. Свайпы листают слои 3…10; свайп после последнего — скрыть всё; Palm_Hold — скрыть немедленно.
7. Память освобождается, префетч готовит следующий пакет слоёв.

**Сценарий B (премиальный стриминг, аналог рекламной вставки):**
1. Зритель в очках смотрит сериал через партнёрское приложение.
2. В согласованный момент платформа присылает `POST /v1/xr-cue`: Video ID Y, таймкод, action=spawn, layer_id.
3. Тот же Thin-Client CDN и рендер-пайплайн отрабатывают триггер — с точки зрения XR-слоя разницы со сценарием A нет.
4. Жесты — тот же словарь из разд. 2: свайпы листают слои, удержание скрывает.
5. Единственная разница — источник первого сигнала: в A его находит телефон, в B присылает партнёр.

## PHASES (обновлены в ред. 3)

**Phase 1 — XR Client: «свитчер слоёв»**
- Поднять базовый Unity/OpenXR проект.
- Написать классификаторы 3 жестов из сырых суставов (Swipe_Right, Swipe_Left, Palm_Hold).
- Парсер JSON-манифеста и свитчер слоёв (слой = State Bundle, переключение <100 мс).
- Head-locked плейсмент; отладка без привязки к видео (тестовая сцена).
- Зафиксировать словарь жестов как версионированный контракт.

**Phase 2 — Сценарий A: «локальная магия»**
- Android Service: MediaProjection + AudioPlaybackCapture (приоритет — аудио-фингерпринтинг).
- Consent UX: объяснение, системный диалог, foreground service, видимый индикатор.
- Prefetch Engine: скачивание слоёв до таймкода, LRU-eviction, бюджет ~10 слоёв.
- Связка распознанного таймкода с XR Timeline (Freeze/Flush на pause/seek/buffering).
- Тюнинг порогов жестов на датасете команды.

**Phase 3 — Сценарий B & Backend: «продакшен и партнёрства»**
- BD-трек: переговоры по контракту `POST /v1/xr-cue` — инженерный старт только после партнёрства.
- Backend: stub-приёмник cue-сигналов с проверкой токенов; санитизация GLB от креаторов.
- Co-Viewing Sync: Redis pub/sub для синхронизации слоёв между зрителями.
- Roadmap-треки (не v1): CV-детектор прямоугольника экрана, 3D Splat-пайплайн.
- **Phase 2.5 (roadmap, дополнение от 2026-09-16):** On-device SLM intent layer — резидентная SLM класса 3B вместо эвристических порогов жестов; gated on железо с ≥12 ГБ unified memory (Android-аналог — Hexagon NPU).

## ИТОГ

Ядро не меняется: pre-baked состояния, переключаемые по триггеру, без физики в реальном времени. В редакции 3 закреплены три архитектурных решения: (1) v1 не пытается трекать живой экран как маркер — head-locked размещение; (2) свайп — это навигация по стеку из ~10 слоёв с фиксированным словарём жестов; (3) сценарий B инженерно заблокирован до BD — с готовым контрактом API для переговоров.
